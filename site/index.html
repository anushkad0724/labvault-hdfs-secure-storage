The data path

From upload to verified download

The controller handles application-level blocks. HDFS then manages its own distributed storage blocks beneath them.

01 / PROTECT

Encrypt every block

Each block is encrypted using AES-GCM with its own random nonce and a file/block identifier for authentication.

02 / STORE

Write to HDFS

Encrypted blocks are saved through WebHDFS. SQLite keeps the file name, block locations, nonces, and digest.

03 / RESTORE

Reassemble and verify

On download, LabVault retrieves each block, checks its authentication tag, joins the original bytes, and verifies SHA-256.

Honest project scope

A prototype to learn from

The running demonstration currently uses one NameNode and one DataNode on one computer. It shows the flow, not production availability.

What it demonstrates

Encrypted file uploads, application-level segmentation, HDFS storage, download and reconstruction, and a separate static site for cloud CDN learning.

For a trusted lab only

Hadoop security is off in this local demo and the controller has no sign-in yet. The HDFS web interface and LabVault should not be exposed to the public internet.
